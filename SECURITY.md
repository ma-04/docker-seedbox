# Security policy

## Reporting a vulnerability

Please report vulnerabilities privately through GitHub: **Security -> Report a vulnerability** on this repository (private vulnerability reporting). Do not open a public issue. Include the version or commit, a description, and reproduction steps. We aim to acknowledge reports within a few days and will credit you in the fix unless you prefer otherwise.

Supported: the latest release and `main`.

## Threat model (summary)

**Trust boundary: header authentication.** The API trusts `Remote-User`, `Remote-Groups`, `Remote-Email` and `Remote-Name`, but only on requests that carry the correct `X-Gateway-Secret`. The gateway:

- strips client-supplied `Remote-*` and `X-Gateway-Secret` and sets its own, so a client cannot impersonate a user;
- with `AUTH_MODE=authelia`, sends every request except `/api/health`, the login portal (`/auth/`) and signed `/dl/` downloads through Authelia (`auth_request`); the portal and `/dl/` also get client-supplied `Remote-*` headers removed, and `/dl/` never passes the browser's `Cookie` or `Authorization` on to the API;
- with `AUTH_MODE=external`, passes `Remote-*` through unchanged. **Then the gateway must be reachable only from your SSO proxy.** Anything that can reach the gateway directly can claim any identity, including admin.

Nothing but the gateway is exposed. `api`, `worker`, `web`, `authelia`, `vpn` and `qbittorrent` have no published ports and live on one internal Docker network. The qBittorrent WebUI is never routed by the gateway.

**Secrets at rest.** Destination credentials, torrent sources and VPN configs are stored AES-256-GCM encrypted in SQLite with a key derived from `APP_SECRET`; the API never returns them (it returns `********`). Losing `APP_SECRET` means losing those values; leaking it together with a copy of the database exposes them. `deploy/.env` is created with mode 600 and must be backed up and kept private. VPN configs are held in memory/tmpfs by the VPN sidecar.

**Signed links.** Local and Cloudflare Worker links are `HMAC-SHA256(key, path + "\n" + exp)` with constant-time verification and optional expiry. `/dl/` (on `APP_HOST`, or on `FILES_HOST` when one is set; never both) answers only `GET/HEAD`, never lists directories, serves files with a sandboxing `Content-Security-Policy`, and gateway access logs for it omit query strings (where signatures travel). Anyone holding a link can download until it expires.

**Revoking links.** Local `/dl` links stop working as soon as the owning job is deleted or not completed, or its owner is disabled (the API checks this on every request after the signature). Cloudflare Worker (Drive proxy) links and S3 presigned links are stateless and cannot be revoked individually: rotate the signing key (`proxySigningKey`) or the S3 credentials, or wait for expiry, so keep `linkTtlSeconds` short. The Worker and `/dl` always answer with `Content-Disposition: attachment`, `nosniff` and a sandboxing CSP, and serve html/svg/xml/javascript as `application/octet-stream`, so uploaded files cannot run script on those origins.

**Hosts and origins.** By default one hostname serves the SPA, `/api`, the Authelia portal (`/auth/`) and local downloads (`/dl/`), so user-supplied file content is served from the same origin as the app and the login portal. What keeps a downloaded file inert there in current browsers:

- every **successful** file response (200/206) carries `Content-Type: application/octet-stream` and `Content-Disposition: attachment`: the API sets both on its `X-Accel-Redirect` answer and nginx keeps them, so the file extension never picks a type;
- **every** `/dl/` response, errors included (the API's 403/404/410 JSON, nginx's own 403/404/416 and its 404 for other methods), carries `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and `Referrer-Policy: no-referrer`; error bodies are short fixed texts, never file content;
- a navigation therefore downloads instead of rendering; were it rendered anyway, the sandbox gives the document an opaque origin with no script; `nosniff` with a non-script type stops `<script src>`, stylesheets and service-worker registration (which requires a JavaScript MIME type), so a file cannot run code in, or take control of paths of, the app's origin; the app registers no service worker of its own;
- Authelia's session cookie is `HttpOnly`, `Secure`, `SameSite=Lax`. The browser does send it with `/dl/` requests on the shared host; the gateway blanks it before the API, nothing echoes it, and neither nginx nor the API logs cookies or the query.

The end-to-end suite checks all of this with an uploaded HTML file containing script (not rendered, not runnable as a script or service worker, no cookie echoed). What a single origin does **not** give you: defence in depth if those headers were ever lost (a proxy or CDN in front that rewrites `Content-Type` or drops CSP, a future regression, a browser bug), and isolation between the SPA and the portal (a script injection in the SPA could act same-origin on the portal pages and its API, e.g. start a 2FA registration, which Authelia still gates behind identity verification). The session cookie's domain is `APP_HOST`, which browsers also send to subdomains of it: do not serve untrusted content under `*.APP_HOST`.

**Separate download host (recommended hardening).** Set `FILES_HOST` (`./setup.sh --files-host dl.example.net`) and local downloads are served only there (`/dl/` on `APP_HOST` answers 404). For real isolation choose a host **outside `COOKIE_DOMAIN`**, ideally a different registrable domain: then the browser neither sends the login cookie with downloads nor treats them as same-site. (The old `files.<domain>` default under a shared parent cookie domain was a different origin, but same-site and inside the cookie's scope.) `AUTH_HOST` moves the portal to its own host as well; it isolates the portal from the SPA's origin but needs a parent cookie domain shared by both, which widens the cookie's scope. See [docs/deployment.md](docs/deployment.md#hosts-layout).

**Request forgery.** Authorisation is decided per matched route (admin routes sit in a guarded plugin), not from the URL text, and raw paths with encoded separators/dots or a differently cased `/api` are rejected. All non-GET `/api` requests must carry `X-Requested-With: seedbox` (CSRF defence in depth on top of same-site cookies).

**Outbound requests (SSRF).** User-owned S3 destinations must use `https` and a public address: loopback, private, CGNAT, link-local, ULA, multicast, documentation/benchmark ranges, IPv4-translated/NAT64/6to4/Teredo forms embedding a non-public address, and bare service names are refused at create, update, test and link generation, and test errors shown to non-admins are reduced to a short category. That API-side check is a pre-flight only (it cannot bind the later connection, and rclone follows redirects), so the worker runs rclone for **user-owned** destinations through an in-process egress proxy that resolves every target itself, refuses it unless every address is public and the port is allowed (`EGRESS_ALLOWED_PORTS`, default 443/80), and connects to the vetted IP. This also covers redirects to internal addresses and DNS rebinding; the API's own S3 SDK calls vet the connect address the same way and never follow redirects. Residual gap: Go never proxies requests to `localhost`/loopback, so an S3 endpoint that redirects to `127.0.0.1` makes rclone connect to the worker container's own loopback directly, without the proxy. This is harmless only while nothing else listens there: the worker's one loopback listener is the egress proxy itself (ephemeral port, 127.0.0.1 only, per-process token required), the API port lives in the separate `api` container, and `worker/loopback.test.ts` fails if another listener appears in the worker code. There is no rclone/Go setting that closes this (`--disable-http2` does not), so keep it that way. Admin-created shared destinations are trusted and connect directly: they may use private addresses and plain `http` (self-hosted MinIO), so only give admin to people you trust. Event streams, destination tests, job creation and destination creation are capped per user to limit abuse.

**Torrent sources.** Magnet links and `.torrent` files are never stored or handed to qBittorrent as submitted. A magnet containing whitespace/control characters or over 8 KiB is rejected and the rest is rebuilt from the infohash, a sanitised name and up to 50 filtered trackers (public-looking `http(s)/udp/ws(s)` hosts only; web seeds, `xs`, `as`, `x.pe` and everything else dropped); uploaded `.torrent` files are parsed by a strict canonical-bencode decoder (duplicate/unsorted keys, non-canonical integers or lengths, trailing bytes, deep nesting, v2/hybrid and symlink torrents are rejected with 400), the infohash is SHA-1 of the raw `info` bytes, the declared size must agree with the piece list, and the stored file is rebuilt from scratch with only `info` and sanitised trackers. This removes the parser differential (two `info` keys / unsorted keys) that could make the app track a decoy while qBittorrent ran another torrent. The worker re-validates every stored source before sending it, fails torrents whose hash does not match their row, removes any torrent the engine runs that matches no row, and sweeps untracked torrents periodically. Magnets must carry exactly one v1 `xt`. This closes a newline injection that made qBittorrent (which splits its `urls` field on newlines) add untracked torrents and fetch arbitrary URLs from inside its network namespace. Tracker hosts are checked without DNS, so a public name that resolves to an internal address is only stopped by the VPN sidecar firewall (which drops every private range in both modes, see below). **Torrents are deduplicated by infohash across all users**: a second user adding a torrent someone else already has may complete instantly, and trackers (including any passkey in a tracker URL) are merged into one shared source. Do not add private-tracker torrents on a shared instance; there is no per-user isolation setting.

**Tracker lists.** Admins (only) can configure up to five list URLs. The URLs must be `https` on public hosts without credentials (checked at save time including DNS), and the worker, not the API or qBittorrent, downloads them: the SSRF guard runs before every request and every redirect hop (at most 3), the TCP connection is pinned to the vetted address, the response is capped at 1 MiB with a 10 s deadline, no cookies or auth are sent, and the User-Agent is just `docker-seedbox`. Every entry is filtered by the same policy as user-submitted trackers (no private, loopback, link-local or single-label hosts, no credentials, schemes `http(s)/udp/ws(s)` only), so a hostile or compromised list can add public trackers only, never point the engine at internal services (and the kill switch drops private ranges regardless). HTML, binary or mostly-invalid bodies are rejected and the previous list kept; stored errors are short fixed messages, never response bodies. Residual risk is privacy: every tracker sees your VPN exit IP and the infohashes you download, so a third-party list widens who learns that. qBittorrent's own "add trackers from URL" preference (fetches without validation inside the VPN namespace) is kept off. qBittorrent skips the extra trackers for private `.torrent` files but not for private magnets (the flag is unknown at add time), so the worker removes them from private magnet torrents after the engine flags them (until then, and for up to ~30 s after the metadata arrives, they are announced to). `TRACKER_LIST_ALLOW_PRIVATE` relaxes the URL rules for the hermetic test stack only; the app refuses to start with it unless `E2E_HERMETIC=1` is also set.

**Logs.** The API logs method and path only: query strings (which carry `exp`/`sig` of signed download links), magnet links and `Authorization`/`Cookie`/`X-Gateway-Secret` headers are never written.

**Deleted data.** Removing a completed job deletes its files from a local destination (confined to the library folder, never while another job references the same folder; the torrent row is marked removed in the same transaction, so a job added meanwhile downloads again instead of failing). Removed S3 job data is only deleted when the admin turns on `cleanup.deleteRemoteOnJobDelete` and no other job of ANY S3 destination resolves to the same endpoint, bucket and full key (deleting a destination never purges remote data); Google Drive data is never deleted automatically.

**VPN kill switch.** One nftables table in the sidecar's network namespace, which qBittorrent shares; there is no uid exemption (root in the qBittorrent container is treated like uid 1000), and IPv6 is dropped in both modes. What each mode enforces:

- `required`: OUTPUT policy drop. Allowed: the `lo` device, the WireGuard UDP endpoint (fwmarked packets only), `wg*` interfaces, and replies to connections the api/worker opened to the WebUI/control ports. Everything private is dropped even through the tunnel, except the tunnel's own DNS servers on port 53 (the provider's DNS is usually a private address such as `10.2.0.1`; the rest of the provider's internal network cannot be probed). Docker's embedded resolver (`127.0.0.11`, on `lo`) is usable by root only, to resolve a WireGuard endpoint hostname.
- `off`: OUTPUT policy accept (internet-direct, no tunnel), with the **same** drops towards private ranges: `LAN_CIDRS`, `10/8`, `172.16/12` (every other Docker bridge, the Docker host at `172.17.0.1`), `192.168/16`, `100.64/10` (CGNAT), `169.254/16` (cloud metadata `169.254.169.254`), `127/8` off the `lo` device, `224/4`, `240/4`, `0/8`, `192.0.0.0/24`, `198.18/15`, and all IPv6. Only the public internet is reachable. RFC 5737 documentation ranges are not blocked (the hermetic test stacks use them as their fake internet).

In both modes: qBittorrent, any URL a user can make it fetch, and a tracker whose public DNS name resolves to a private address cannot open a connection to the host, a sibling container or the provider network; INPUT from the compose subnet reaches only the WebUI port and the control port (the latter only from the api and worker addresses); input from the tunnel to those ports is dropped; the WebUI accepts password-less requests only from the api and worker addresses. libtorrent's SSRF mitigation is re-asserted on every start. `POST /connect` is refused while the mode is `off`. Run `./setup.sh doctor` and verify your public IP from inside the namespace after configuring a VPN. `VPN_LAN_ALLOW_OUT` punches holes in these rules for the hermetic test fixtures only; never set it on a real deployment. Not enforced: a provider whose DNS or other required service sits on a private address other than the configured `DNS =` servers is not supported.

**Least privilege.** Every container drops all Linux capabilities and adds back only what it needs (`vpn`: `NET_ADMIN`; `qbittorrent`: `CHOWN` (the `/config` volume's top directory only), `SETUID`/`SETGID` (drop to uid 1000) and `KILL` (tini forwards SIGTERM), no `DAC_OVERRIDE`/`FOWNER`; `authelia` and the bundled `nginx-proxy`: what their entrypoints need; the bundled `acme-companion` keeps Docker's default set). All set `no-new-privileges`. The qBittorrent container has a **read-only root filesystem** (writable: `/config`, the `incomplete/` subpath, a `/tmp` tmpfs), so its entrypoint cannot be replaced, and everything under `/config` (seeding `qBittorrent.conf`, qBittorrent itself) is written by uid 1000, never by root: the qBittorrent user owns `/config` and can plant symlinks there, which a root-run entrypoint used to follow (e.g. `qBittorrent.conf.tmp` -> `/entrypoint.sh`, executed as root on restart; root in that namespace was also exempt from the LAN rules). qBittorrent, which parses untrusted network input, mounts only the `incomplete/` subtree of the downloads volume; the gateway gets `library/` read-only, the api `library/` only: a compromised qBittorrent cannot read or alter the delivered files of other users (the worker is the only service that sees both). Because qBittorrent can plant symlinks, FIFOs and hardlinks in `incomplete/`, the worker resolves every content path with `realpath` (it must stay inside the real `incomplete/<infohash>`), delivers only regular files and directories (it `lstat`s every entry, skips everything else and files with several hard links, opens files with `O_NOFOLLOW` and checks the descriptor, moves content through a worker-only staging directory and re-vets it there, and hands rclone an explicit vetted file list), and the gateway serves the library with `disable_symlinks on`. Residual: a directory swapped for a link in the instant between vetting and an rclone upload of live data is not detectable for rclone destinations (the local copy path checks every opened file). nginx writes its access log without query strings on every host (magnet links, signatures and Authelia `rd=` targets stay out); its error log still prints the request line of failed requests, so keep log retention short.

**Supply chain.** Images are published only from `v*` tags (or `main` as `:edge`) after the full CI suite, including the end-to-end tests, passed for that commit; both architectures (amd64, arm64) are built natively on GitHub-hosted runners without emulation and smoke-tested on their own architecture, all five images are pushed untagged and only then merged and tagged, so a failed build cannot leave a mixed set under `:latest`. Releases carry SBOMs and signed build-provenance attestations (`gh attestation verify`, see [docs/deployment.md](docs/deployment.md#versions-upgrades-and-verification)). GitHub Actions are pinned to commit SHAs, base images to digests, and Dependabot proposes updates. `setup.sh` keeps a non-secret fingerprint of `APP_SECRET` next to the database and refuses to start with a different secret, validates every input as a whole string (no newline/control-character injection into `.env` or the Authelia users file) and creates its files with `umask 077`; it refuses `AUTH_MODE=external` with the bundled proxy unless explicitly told otherwise. Third-party licenses: [THIRD_PARTY_LICENSES.md](THIRD_PARTY_LICENSES.md).

**Docker socket.** The app stack never mounts it. The optional bundled proxy mode (`compose.proxy-bundled.yaml`) mounts it into nginx-proxy and acme-companion (with `:ro`, which only prevents replacing the socket file; it does not restrict what the Docker API allows). Access to the socket is effectively root on the host, so use `external` or `none` mode if you do not accept that.

**Out of scope / your responsibility:** host hardening, TLS/DNS at your edge proxy, who you give accounts to (any logged-in user can add torrents and consume disk and bandwidth within the configured limits), and the legality of downloaded content.
